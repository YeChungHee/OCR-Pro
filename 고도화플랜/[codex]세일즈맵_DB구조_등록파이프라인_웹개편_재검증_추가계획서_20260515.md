## 1. 재검증 결론

Claude 검증보고서가 v9.43 기준으로 갱신되었고, 현재 프로젝트의 단일 기준 파일도 `index.html` v9.43으로 정리되었다. 따라서 v9.44 구현 기준은 더 이상 `/tmp/ocr-pro-deploy/index.html`이나 `ocr-pro-v51.html`이 아니라 프로젝트 루트의 `index.html` 하나다.

v9.43 기준 최종 판정:

| 항목 | 판정 | v9.44 반영 |
|---|---|---|
| Organization fieldList에 전화/웹 주소 누락 | 유효 | 즉시 수정 |
| People 생성 조건이 `전화 또는 이메일 필수` | 유효 | `peopleName` 기준으로 완화 |
| People 미등록 사유 UI 경고 | 부분 개선됨 | 유지 |
| People POST 실패가 `console.warn`만 남음 | 유효 | UI 로그/toast 반영 |
| SalesMap read-back 검증 없음 | 유효 | capability probe 후 구현 |
| `웹 주소` 필드명 혼재 | 유효 | fieldList는 공백 포함 `웹 주소` |
| v9.44에 UI 대개편 포함 | 범위 과다 | v9.46으로 이동 |

## 2. v9.43 코드 기준 확인

### 2.1 현재 버전

`index.html` 기준:

- `<title>`: `OCR Pro v9.43 — 핵심 필드 우선순위 학습`
- 버전 배지: `v9.43`
- 최신 파일 해시: `861eea7b879d58da52d43ed82354d3b1`

### 2.2 현재 SalesMap 엑셀 출력

`exportExcel()`은 이미 SalesMap 엑셀 구조를 비교적 정확히 갖고 있다.

주요 컬럼:

- `Organization - 이름`
- `Organization - 사업자번호`
- `Organization - 대표자명`
- `Organization - 담당직원`
- `Organization - 전화`
- `Organization - 주소`
- `Organization - 웹 주소`
- `People - 이름`
- `People - 직함`
- `People - 전화`
- `People - 이메일`

따라서 v9.44에서는 이 엑셀 출력 구조를 기준으로 API 직접 등록 payload를 맞춰야 한다.

### 2.3 현재 SalesMap 직접 등록

현재 `pushToSalesmap()`의 Organization fieldList에는 다음이 없다.

- `전화`
- `웹 주소`
- `주소`

현재는 아래처럼 top-level fallback만 사용한다.

```js
...(r.웹주소    ? { website: r.웹주소 }    : {}),
...(landlineTel ? { phone: landlineTel }    : {}),
...(r.주소      ? { address: r.주소 }       : {}),
```

실제 SalesMap 화면에서 `전화`, `웹 주소`가 비어 있는 문제가 있으므로 v9.44에서는 fieldList에도 명시해야 한다.

## 3. 필드명 확정

### 3.1 회사 Organization 필드

SalesMap 화면과 엑셀 헤더를 기준으로 다음 필드명을 사용한다.

| OCR Pro 내부 필드 | SalesMap fieldList name | 설명 |
|---|---|---|
| `회사명` | top-level `name` | 회사명 |
| `사업자번호` | `사업자번호` | 사업자등록번호 |
| `대표자` | `대표자명` | 대표자 |
| `담당자` | `담당직원` | 담당자/담당직원 |
| `전화` 일반번호 | `전화` | 02/031/070 등 회사 전화 |
| `웹주소` | `웹 주소` | 공백 포함 |
| `주소` | `주소` | 회사 주소 |
| `_expoIndustryText` | `아이템` | 취급품목/주력사업 원문 |
| `source` | `유입경로` | 오프/행사 또는 전시회 |
| `exhInput/부스번호` | `유입경로_상세` | 전시회명/부스 |

중요 보정:

- Claude 보고서 예시에는 `일반전화`라는 필드명이 등장하지만, 현재 SalesMap 화면과 기존 엑셀 출력은 `전화`다.
- 별도 SalesMap 사용자 정의 필드가 `일반전화`로 존재한다는 증거가 없으면 `전화`를 사용한다.
- `웹 주소`는 공백 포함이 맞다.

### 3.2 개인 People 필드

| OCR Pro 내부 필드 | SalesMap 저장 | 설명 |
|---|---|---|
| `담당자` 또는 `대표자` | People `name` | 개인명 |
| `담당직함` | fieldList `직함` | 직함 |
| `휴대폰` 또는 010 번호 | top-level `phone` + fieldList `전화` | 개인 전화 |
| `이메일` | top-level `email` + fieldList `이메일` | 개인 이메일 |
| `orgId` | `organizationId` | 연결회사 |

People은 전화/이메일이 없어도 이름이 있으면 생성한다. 다만 마케팅 상태는 `보완 필요`로 표시한다.

## 4. v9.44 구현 계획

v9.44는 UI 대개편이 아니라 SalesMap 저장 정확도 핫픽스다.

### 4.1 공통 builder 추가

`exportExcel()`과 `pushToSalesmap()`가 같은 필드 라우팅을 쓰도록 공통 함수를 만든다.

```js
function buildSalesMapPayload(record, context = {}) {
  const routed = routeSalesMapFields(record, context);
  return {
    organization: buildOrganizationPayload(routed),
    people: buildPeoplePayload(routed),
    completeness: evaluateSalesMapCompleteness(routed)
  };
}
```

### 4.2 중복 fieldList 방지

```js
function addFieldOnce(fieldList, name, value) {
  const v = String(value || "").trim();
  if (!v) return;
  const existing = fieldList.find(f => f.name === name);
  if (existing) existing.stringValue = v;
  else fieldList.push({ name, stringValue: v });
}
```

### 4.3 Organization payload

v9.44에서 Organization fieldList는 최소 다음을 포함한다.

```js
addFieldOnce(fieldList, "대표자명", 대표자명);
addFieldOnce(fieldList, "담당직원", 담당직원);
addFieldOnce(fieldList, "담당직함", 담당직원 ? 직함원본 : "");
addFieldOnce(fieldList, "사업자번호", r.사업자번호);
addFieldOnce(fieldList, "전화", landlineTel);
addFieldOnce(fieldList, "주소", r.주소);
addFieldOnce(fieldList, "웹 주소", r.웹주소);
addFieldOnce(fieldList, "아이템", r._expoIndustryText);
addFieldOnce(fieldList, "유입경로", r.source === "전시회" ? "전시회" : "오프/행사");
addFieldOnce(fieldList, "유입경로_상세", detailSource);
```

top-level fallback도 유지한다.

```js
const orgBody = {
  name,
  ...(r.웹주소 ? { website: r.웹주소 } : {}),
  ...(landlineTel ? { phone: landlineTel } : {}),
  ...(r.주소 ? { address: r.주소 } : {}),
  fieldList
};
```

### 4.4 People payload

현재 v9.43은 `peopleName && (mobileTel || peopleEmail)` 조건이다. v9.44에서는 `peopleName`만 있으면 생성한다.

```js
if (peopleName) {
  const pfList = [];
  addFieldOnce(pfList, "직함", people직함);
  addFieldOnce(pfList, "전화", mobileTel);
  addFieldOnce(pfList, "이메일", peopleEmail);

  const peopleBody = {
    name: peopleName,
    ...(peopleEmail ? { email: peopleEmail } : {}),
    ...(mobileTel ? { phone: mobileTel } : {}),
    ...(orgId ? { organizationId: orgId } : {}),
    ...(pfList.length ? { fieldList: pfList } : {})
  };
}
```

전화/이메일이 모두 없으면 생성은 하되 UI 로그에 다음처럼 표시한다.

```text
⚠️ People 생성됨 — 연락처/이메일 보완 필요
```

### 4.5 People 실패 UI 반영

현재는 `console.warn`만 남는다. v9.44에서는 다음을 추가한다.

- 현재 행 로그에 `People실패` 표시
- 최종 결과 카운트에 `peopleErrCount` 추가
- toast는 과도한 반복을 피하기 위해 전체 완료 후 요약 1회 표시

## 5. read-back 검증 계획

### 5.1 전제

SalesMap API가 POST 이후 반환한 ID로 GET 조회를 지원하는지 아직 확정되지 않았다. 따라서 v9.44 구현은 다음 순서로 진행한다.

1. POST 응답의 ID 추출
2. by-id GET 가능 여부 probe
3. by-id가 불가하면 search fallback 사용
4. 둘 다 필드 상세를 반환하지 않으면 `검증불가`로 표시

### 5.2 검증 대상 필드

Organization:

- 회사명
- 사업자번호
- 전화
- 웹 주소
- 주소

People:

- 이름
- 전화
- 이메일
- 연결회사

### 5.3 결과 상태

| 상태 | 의미 |
|---|---|
| 등록완료 | 레코드 생성 + 핵심 필드 read-back 일치 |
| 부분등록 | 레코드 생성 + 일부 필드 누락 |
| 등록성공_검증불가 | 레코드 생성 성공, API가 필드 조회를 제공하지 않음 |
| 등록실패 | Organization 생성 실패 |
| People실패 | Organization 성공, People 실패 |
| 보완필요 | People 생성됐지만 이메일/전화 없음 |

## 6. v9.46 UI 개편으로 이동할 항목

다음은 v9.44에서 하지 않는다.

- 전체 테이블을 Organization/People 이중 그룹으로 대개편
- 마케팅 상태 배지 정교화
- payload preview 전용 상세 패널
- 화면 레이아웃 재설계

단, v9.44에서도 최소한의 결과 로그는 개선한다.

- Organization 등록 상태
- People 등록 상태
- 누락 필드 요약
- 검증 가능/불가 여부

## 7. 이메일 마케팅 기준 보강

모든 입력 파이프라인의 최종 목적은 이메일 마케팅을 위한 기초 DB 생성이다. 따라서 v9.44 이후 레코드 품질은 OCR 신뢰도가 아니라 SalesMap 저장 가능성으로 평가한다.

### 7.1 핵심 저장 가능성

| 등급 | 조건 |
|---|---|
| A | 회사명 + People 이름 + 이메일 |
| B | 회사명 + People 이름 + 휴대폰 |
| C | 회사명 + 웹 주소 |
| D | 회사명만 있음 |
| 보류 | 회사명 없음 |

### 7.2 파이프라인별 차이는 저장 전 정규화에서 흡수

명함, QR, 문서, URL, 전시회는 추출 방식이 다르지만, SalesMap 등록 전에는 모두 다음 정규화 구조로 들어와야 한다.

```js
{
  organization: { name, businessNo, phone, website, address },
  people: { name, title, mobile, email },
  source: { pipeline, eventName, sourceUrl, confidence }
}
```

## 9. 구현 우선순위

1. `addFieldOnce()`와 공통 payload builder 작성
2. Organization fieldList에 `전화`, `웹 주소`, `주소` 추가
3. People 생성 조건 완화
4. People fieldList에 `전화`, `이메일`도 함께 넣기
5. People 실패 UI 반영
6. read-back capability probe 추가
7. v9.44 버전 배지/CHANGELOG 반영
8. 샘플 7건으로 SalesMap 저장 결과 재검증

## 10. 최종 권고

Claude 재검증보고서의 v9.43 기준 지적은 대부분 유효하다. 다만 구현 시 `일반전화`라는 새 필드명을 만들지 말고 현재 SalesMap 화면과 엑셀 구조에 맞춰 `전화`를 사용해야 한다. `웹 주소`는 공백 포함으로 확정한다.

v9.44는 `저장 누락 방지`가 목표다. 웹페이지 전체 개편은 v9.46으로 미루고, 지금은 SalesMap DB에 이메일 마케팅용 핵심 필드가 실제 저장되는지부터 해결한다.
